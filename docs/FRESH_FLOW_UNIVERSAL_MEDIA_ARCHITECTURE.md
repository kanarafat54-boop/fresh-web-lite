# Fresh Flow — Universal Media Ecosystem Architecture

**Status:** Architecture contract / implementation blueprint  
**Product:** Fresh Flow inside Fresh Web Lite  
**Decision:** Fresh Flow is the single canonical home for all media and media-related experiences.  
**Scope rule:** “All” is open-ended: current, emerging, future and not-yet-imagined formats and workflows must be representable without replacing the navigation model or redesigning the core platform.

## 1. The non-negotiable product definition

Fresh Flow is not a video feed, a collection of six tabs, or a closed catalogue of file types. It is the media operating environment for discovering, creating, transforming, sharing, experiencing, discussing, preserving and monetizing media.

The six current destinations—Home, Long Videos, News/Posts, AR/VR, Podcasts and Others—are **entry points and presentation modes**, not architecture boundaries. Shorts remains a format and specialized playback path inside Fresh Flow, not a separate product or a second media system.

“All media” includes media payloads, live experiences, interactive experiences, hybrid physical/digital experiences, media creation tools, distribution, collaboration, accessibility, provenance, rights, community, analytics and creator economy. New categories must be able to register as capabilities rather than requiring a closed enum, new top-level navigation item, or duplicate backend.

This contract is deliberately extensible; it does not claim every capability is already implemented. Each capability must expose its actual status and required providers/devices clearly.

## 2. Architecture principles

1. **One ecosystem, many renderers.** A shared identity, asset, policy, discovery, interaction and event model supports specialized experiences.
2. **Open-world taxonomy.** Identifiers are stable strings/namespaces, not exhaustive unions. Unknown types can be safely catalogued, previewed as metadata, routed to a compatible handler, or presented as unsupported without crashing.
3. **Capability before promise.** Registration describes support; it never grants authorization or proves a provider exists.
4. **Composition over category explosion.** An experience can combine video + spatial audio + live chat + polls + 3D objects + captions, without inventing a separate monolithic type for every combination.
5. **Separate control plane and media data plane.** Identity, policy, metadata, jobs, entitlements and event coordination are distinct from large binary delivery and real-time media transport.
6. **One source of truth for durable state.** Postgres stores authorized durable records; object storage stores media bytes and derivatives; realtime transports events, not the canonical history.
7. **User sovereignty and safety.** Ownership, visibility, consent, rights, safety, audience, data use and monetization policy apply across every renderer and API.
8. **Degrade honestly.** Unsupported codec, missing provider, permission denial, weak network or unavailable feature produces a clear fallback, not fake content or fake metrics.
9. **Mobile-first and bandwidth-aware.** Core browse/read/listen/create journeys must work on modest Android devices, weak networks and interrupted sessions.
10. **Accessibility is part of the media contract.** Captions, transcripts, alt text, keyboard/screen-reader semantics, scalable text, reduced motion, localization and RTL are declared and tested.
11. **Replaceable infrastructure.** Storage, CDN, transcoder, live transport, search, recommendation and payment providers sit behind versioned adapters.
12. **Future inventions fit the model.** New sensory channels, codecs, spatial formats, interaction patterns or media generated by future devices can be described by capability descriptors, manifests and composable tracks.

## 3. Open-world media and experience taxonomy

The following is a **starter map, not a limit**. Implementations may add namespaces at any time subject to validation, policy, security review and adapter contracts.

### 3.1 Text, language and documents
- Plain/rich text, micro-posts, long-form articles, threads, notes, journals, newsletters, serialized writing, comments and annotations.
- Documents, PDFs, e-books, scanned pages, presentations, spreadsheets, forms, manuals, reports, research papers, code, structured data and interactive documents.
- Live text, collaborative writing, shared whiteboards, text adventures, branching narratives, hypertext, timelines, knowledge maps and mixed text/media stories.
- Translation, transliteration, summaries, accessible reading modes, text-to-speech and speech-to-text derivatives.

### 3.2 Still and sequential visual media
- Photos, illustrations, drawings, diagrams, infographics, charts, memes, stickers, emoji compositions, icons, scans, artwork and visual notes.
- Albums, galleries, carousels, comics, manga, graphic novels, storyboards, contact sheets, image sequences, panoramas, 360-degree imagery, deep zoom and gigapixel imagery.
- Layered, editable, vector, procedural, generative and interactive visual compositions; image sets with metadata, annotations and provenance.

### 3.3 Moving image and temporal visuals
- Shorts, vertical clips, long-form films, episodes, series, trailers, documentaries, animation, screencasts, tutorials, lectures, sports, news footage, music videos and user-generated video.
- Slow motion, time-lapse, stop motion, multi-camera cuts, picture-in-picture, synchronized multi-angle playback, 360 video, volumetric video, light-field and other future capture formats.
- Looping clips, stories, temporary media, chapters, playlists, compilations, remixes, clips, highlights and timestamped annotations.
- Adaptive bitrate and codec/rendition variants, subtitles, captions, chapters, transcripts, audio-description tracks and alternate language tracks.

### 3.4 Audio, voice and music
- Music, albums, singles, playlists, mixes, radio, DJ sets, live audio, voice notes, audiobooks, spoken-word, poetry, ambient sound, soundscapes, field recordings and sound effects.
- Podcasts, episodes, interviews, lectures, lessons, news bulletins, audio drama, guided sessions, language practice and multi-speaker conversation.
- Spatial/binaural audio, multi-track/stems, synchronized lyrics where rights permit, sound design, audio-reactive visuals and interactive audio.
- Background playback, queue management, speed control, sleep timers, transcript alignment, speaker labels and offline downloads where licensed.

### 3.5 Live experiences — first-class, distinct lifecycle types
“Live” is not one boolean or one provider. Each live experience declares its topology, roles, transport, latency target, moderation model, recording policy and reconnect behavior.

- One-to-many broadcast: creator stream, concert, sports, news, worship, lecture, product launch, public event.
- Interactive broadcast: chat, reactions, polls, Q&A, captions, co-host invitations, moderated audience participation.
- Two-way and multi-party audio/video: calls, rooms, interviews, meetings, panels, classrooms, consultation and collaboration sessions.
- Audio-only rooms, live podcast recording, radio, listening parties and synchronized watch/listen parties.
- Gaming/esports streams, spectator modes, tournaments, co-play and game-linked overlays.
- Live shopping, auctions, demonstrations, ticketed sessions, classes and creator events.
- Screen sharing, coding sessions, remote demonstrations, virtual workshops and support sessions.
- Spatial/immersive live: VR rooms, volumetric/spatial presence, shared 3D scenes, AR overlays and synchronized world events.
- Location/field-based live, mobile reporting, multi-camera contribution, remote guest feeds and hybrid in-person/remote events.
- Machine/event streams, sensor visualization and future real-time media sources when safe and appropriate.
- Scheduled, waiting-room, rehearsal, active, paused, reconnecting, ended, processing, replay-ready, failed and cancelled states.

Every live implementation must identify the actual provider/protocol and must not display fabricated viewer counts or “Live now” claims. Recording, replay and clips are separate consent- and rights-aware assets.

### 3.6 Interactive, playable and executable experiences
- Games, browser-based experiences, interactive stories, choose-your-path narratives, puzzles, quizzes, simulations and educational exercises.
- Live game overlays, audience-controlled interactions, virtual stages, interactive streams, shared canvases and collaborative editors.
- Web-based interactive media, data-driven visualizations, safe embedded experiences, programmable art and future executable formats.
- Sandboxed execution, capability permissions, resource budgets, origin isolation, content signing, review, abuse prevention and kill switches are mandatory where code executes.

### 3.7 Spatial, immersive and embodied media
- AR, VR, MR, XR, 3D models/scenes, avatars, virtual worlds, spatial rooms, digital twins, 3D scans, CAD/design previews and interactive product models.
- Motion capture, volumetric capture, spatial audio, gesture/pose-driven interaction, haptics and other device-dependent channels.
- Device/browser capability negotiation; fallback to 2D preview, video walkthrough, still images or descriptive text when immersive hardware is unavailable.
- Explicit permission and safety boundaries for camera, microphone, location, motion sensors and other device APIs.

### 3.8 Hybrid, synchronized and multimodal experiences
- A single experience can combine text, image, video, audio, captions, translations, documents, live events, spatial assets, interactive widgets and data streams.
- Synchronized timelines, multi-track assets, sidecars, alternate viewpoints, branching paths, annotations, polls, commerce, live chat and accessibility tracks.
- Composite experiences reference independently governed child assets and declare synchronization, versioning, fallbacks and per-track rights.

### 3.9 Creation, transformation and media operations
- Capture, import, upload, resumable upload, trim, crop, edit, compose, annotate, caption, translate, dub, transcribe, normalize, remix, render, convert, compress, enhance, repurpose, schedule, publish, unpublish, archive and delete.
- Drafts, templates, reusable projects, collaborative editing, version history, review queues, batch processing and scheduled releases.
- AI-assisted creation and transformation are tools with provenance, consent, rights checks, user controls and explicit status—not an excuse to claim unavailable generation.
- Processing is a job graph with observable stages, bounded retries, cancellation, idempotency and recoverable failure.

### 3.10 Community, learning, commerce and knowledge experiences
- Reactions, comments, threaded discussion, annotations, bookmarks, collections, playlists, follows, subscriptions, memberships, clubs, communities and co-creation.
- Courses, lessons, assessments, live classrooms, study groups, tutorials, research collections and knowledge bases.
- Tickets, events, product showcases, live shopping, affiliate links, creator offers, licensed media, commissions and digital/physical goods where supported.
- Searchable claims, sources, provenance, corrections, contextual references and user-controlled knowledge collections.

### 3.11 Future and unknown formats
- Unknown media identifiers and MIME types must be preserved as metadata when safe; do not silently coerce or discard them.
- Capability descriptors may declare novel renderers, editors, processors, transports, sensors, codecs, actions, input/output channels and accessibility adaptations.
- Unknown executable or active content must never run automatically. It remains quarantined/metadata-only until validation and explicit policy approval.
- New media formats should normally be introduced through a versioned capability registration and adapter package, not changes to core feed navigation, identity, database authorization or interaction tables.

## 4. Universal media object model

A media item is a versioned, permissioned **media object**. The object represents identity and meaning; binary files and playback-specific renditions are assets attached to it.

Minimum conceptual fields:

- `id`, `tenant/workspace scope`, `owner/creator identity`, `created_at`, `updated_at`, `schema_version`.
- `media_type` and `media_subtype`: stable extensible namespaced strings, not a closed enum.
- `title`, `description`, `language(s)`, `tags`, `topics`, `people/entities`, `content warnings`.
- `visibility`, `audience rules`, `publication state`, `moderation state`, `age/region restrictions` where legally required.
- `rights/license`, `consent evidence`, `attribution`, `source/provenance`, `derivation lineage`, `AI/transformation disclosure` where applicable.
- `asset manifest`: originals, renditions, thumbnails, waveforms, captions, transcripts, posters, sidecars, spatial resources and checksums.
- `capability requirements`, `renderer hints`, `fallbacks`, `duration/dimensions/channels`, `codec/MIME`, `size` and safe technical metadata.
- `relationships`: replies, series/episodes, collection membership, remixes, translations, clips, citations, synchronized components, parent/child assets and versions.
- `interaction summary` is derived/cached; authoritative reactions/comments/saves remain durable records.
- `availability`, `retention`, `deletion/tombstone`, `legal hold` and audit references where applicable.

Do not put media binaries in relational rows. Store bytes in object storage; store authorized metadata and relationships in Postgres; use CDN delivery and short-lived signed access where needed. A URL is not authorization.

### Asset and derivative lineage
Each source asset and derivative has its own stable ID, checksum, media type, technical metadata, rights, creation method, processing job, parent references and retention policy. Transformations must not erase provenance or imply ownership of source material the creator does not own.

## 5. Logical system architecture

### A. Client and experience layer
- Fresh Flow shell and navigation entry points.
- Discovery surfaces: personalized, following, newest, topic, local/nearby when explicitly permitted, editorial, search, collections and accessible modes.
- Renderer registry: image, text, document, audio, video, live, spatial, interactive and unknown-safe fallback renderers.
- Playback coordinator: one active viewport owner, queue/cursor, prefetch budget, background-audio ownership, resume state and lifecycle handling.
- Creator workspace: library, drafts, capture/import, editor, jobs, publishing, audience and analytics.
- Personal/workspace switcher; developer console; admin/operator tools; contextual Fresh AI assistant.
- Data saver, low-memory mode, offline-aware state and clear retry/error states.

### B. Edge/API and authorization layer
- Authenticated API gateway or server actions; schema validation and request-size limits.
- Authentication establishes identity; server authorization checks ownership, membership, role, audience, consent, rights and entitlements for every operation.
- Rate limits, quotas, abuse controls, idempotency keys, audit events and safe error responses.
- Signed upload/download grants with expiry and narrow scope; secrets and provider credentials stay server-side.
- Separate public discovery/read endpoints from private library, drafts, messages, analytics, developer keys and admin operations.

### C. Domain services
Keep domain boundaries explicit even if the first implementation deploys as a modular monolith:
1. Media catalog and asset manifest.
2. Upload and ingestion orchestration.
3. Processing/transformation job coordinator.
4. Publication, scheduling and distribution.
5. Discovery/search and ranking.
6. Durable interactions and collections.
7. Live session lifecycle and provider adapters.
8. Identity/workspaces and audience/entitlement evaluation.
9. Moderation, reports, appeals and rights management.
10. Analytics/events with privacy and retention controls.
11. Creator economy, ledger, offers, refunds and payouts.
12. Notifications, realtime signaling and webhooks.
13. AI tool orchestration and provenance.
14. Developer API credentials, quotas, environments and logs.

### D. Data and delivery layer
- Postgres/Supabase for durable metadata, relationships, jobs, interactions, permissions, audit references and transactional ledger records.
- Object storage for originals and derivatives; CDN for cacheable delivery.
- Search index as a rebuildable projection of authorized source records.
- Queue/job system for heavy processing; workers own transcoding/rendering, not browser UI.
- Realtime Broadcast/signaling for ephemeral events; durable state is separately persisted.
- Provider adapters for live transport, codecs/transcoding, notifications, search, AI, storage/CDN and payments. A provider adapter is not a claim that the provider is configured or free.

## 6. End-to-end media lifecycle

1. **Intent and permission:** user chooses create/import/live action; explain permissions and rights.
2. **Ingest:** validate size, MIME/signature, extension, checksum, quotas, malware/policy scan and ownership; unknown active formats quarantine safely.
3. **Register:** create asset/media-object records and initial state; issue scoped upload grants.
4. **Process:** enqueue versioned job graph; create previews, thumbnails, transcodes, captions, transcripts, waveform, metadata extraction and accessibility derivatives as appropriate.
5. **Review:** moderation, rights, consent, safety and policy checks; route uncertain cases to human review.
6. **Publish:** validate metadata/audience, schedule or publish idempotently; invalidate/update authorized discovery projections.
7. **Discover:** apply privacy, safety, freshness, relevance, diversity and user controls before ranking; do not leak private metadata through search.
8. **Experience:** negotiate device/network/provider capabilities; choose rendition and renderer; expose controls, captions and fallbacks.
9. **Interact:** durable actions persist in canonical stores; transient events use realtime transport; enforce authorization at write time.
10. **Measure:** privacy-bounded analytics with definitions and anti-fraud controls; never fabricate viewer counts, reach or earnings.
11. **Transform/remix:** preserve source rights, attribution, consent and lineage; publish derivative as a distinct asset/object.
12. **Archive/delete:** honor retention, legal obligations and deletion propagation to derivatives, caches, search projections and provider copies.

## 7. Live session architecture

A live session is a separate object linked to media assets and an event/session lifecycle. Minimum states: `draft`, `scheduled`, `waiting`, `live`, `paused`, `reconnecting`, `ended`, `processing_replay`, `replay_ready`, `failed`, `cancelled`.

A session descriptor includes:
- Stable session ID, host/owner, co-hosts, moderators, audience rules and participant roles.
- Experience topology (broadcast, multi-party, audio room, screen share, game, spatial, hybrid, etc.).
- Provider adapter and protocol, region, latency class, media tracks, codecs and device requirements.
- Chat/reaction/poll/Q&A policies, moderation controls, recording/clip consent, replay rights and retention.
- Start/end times, heartbeat/health, reconnect policy, limits, failure reason and audit references.
- Viewer/participant metrics only from validated provider/session telemetry with clear semantics and anti-abuse rules.

Creation, joining, publishing tracks, inviting speakers, recording, moderation and ending sessions are separately authorized operations. Never trust a client-supplied viewer count or host identity. Provider outage must not corrupt durable session history.

## 8. Discovery, ranking and search

Discovery is a shared service with replaceable ranking policies, not logic duplicated in each tab. Candidate sources include follows, topics, search, public catalogs, subscriptions, live schedules, editorial picks, learning paths and creator libraries.

Mandatory gates precede ranking:
- Visibility, owner/audience permissions, blocks/mutes, age/region restrictions and consent.
- Moderation status, rights restrictions, safety constraints and user controls.
- Capability/device compatibility and bandwidth/data-saver preferences.

Ranking signals can include relevance, freshness, explicit user intent, completion, quality, affinity, diversity, novelty, language, accessibility, creator distribution fairness and repeated-exposure controls. Explainable controls must allow users to adjust personalization. Do not treat watch time as the sole objective or let ranking override safety.

Search indexes are derived projections. Re-check authorization at result/open time. Support text and metadata first; add image/audio/video/spatial similarity only behind tested providers, privacy rules and clear availability states.

## 9. Universal interaction and event model

Use stable namespaced targets and actions; avoid requiring a new database enum for every new media type. Interactions may include react, reply, comment, quote, annotate, bookmark, save, share, follow, subscribe, remix, report, vote, attend, join, invite, co-create and future actions.

- Durable records: ownership, reactions, comments, saves, follows, memberships, publication changes, consent and financial ledger entries.
- Ephemeral events: typing, cursor movement, transient reactions, presence and low-latency signaling.
- Realtime delivery is not proof of persistence; retries and duplicate events require idempotency.
- Validate target visibility and actor permission on every write.
- Counters are derived/cached from canonical data or trusted provider telemetry; they are not client authority.
- Privacy, deletion, moderation and retention policies apply consistently across feeds, search, notifications and analytics.

## 10. Security, privacy, rights and trust

- RLS and server authorization are defense in depth; verify owner, member, other-user and privileged-role cases.
- Do not place service-role keys, provider secrets, unredacted credentials or private media URLs in client bundles/logs.
- Use signed, short-lived upload/download grants and least-privilege object storage policies.
- Treat uploaded files, external embeds, subtitles, metadata, interactive code and AI outputs as untrusted input.
- Sandbox active/executable content; enforce content security policies, origin isolation, resource limits and kill switches.
- Record consent and rights for recording, remixing, face/voice likeness, music, location and sensitive media.
- E2EE must only be claimed for a capability with an implemented and verified key lifecycle/protocol; TLS and managed at-rest encryption are not E2EE.
- Provide reporting, blocking, appeals, takedown, provenance and auditable privileged actions.
- Support account export/deletion and propagate deletions according to legal retention rules.
- Do not expose private messages or private analytics to admins without explicit case-scoped authorization and audit.

## 11. Creator economy and monetization

Monetization is a shared service, not a hardcoded media-type feature. Possible instruments include ads, subscriptions, memberships, tips, gifts, tickets, paid live sessions, courses, commerce, licensing, affiliate referrals, commissions and revenue sharing. These are extensible possibilities, not a promise that each provider/country/feature is currently available.

Every instrument requires eligibility rules, jurisdiction/provider availability, fees and taxes disclosure, consent, fraud controls, refunds/chargebacks, payout state, ledger reconciliation, idempotency and audit. Balance and earnings UI must come from an auditable ledger/provider response; never simulated values. Creator analytics must define metrics and respect privacy.

## 12. Capability descriptor and adapter contract

Each capability registration should declare:
- Stable namespaced ID and version; display name and user outcome.
- Media types/MIME signatures handled and safe unknown-type behavior.
- Supported actions, renderer/editor/processor/transport adapters.
- Input/output tracks and composition relationships.
- Provider, device, permission, codec and feature requirements with fallbacks.
- Accessibility support and available alternate representations.
- Rights/consent/moderation requirements and data classification.
- Availability state: `available`, `provider-required`, `device-required`, `planned` or `disabled`.
- Limits, resource budget, compatibility, error contract and health/telemetry signals.

Registration is metadata only. Server policy authorizes every operation. Adapter interfaces must be versioned, cancellable, testable and safe to remove or replace. An unsupported adapter must degrade to metadata/preview, not break the feed.

## 13. UX and accessibility contract

Every screen and renderer must support:
- Loading, empty, offline, permission-denied, unsupported, processing, failed, retry and expired states.
- Large discoverable controls and touch targets; scalable text; strong contrast; screen-reader labels; keyboard/focus order.
- Captions/transcripts, image descriptions, audio description where relevant, language selection and reduced motion.
- Data saver, adaptive quality, resumable uploads, bounded prefetch and explicit download/storage controls.
- Clear controls for autoplay, background playback, notifications, camera/microphone/location, personalization and data usage.
- Localization/time zones, RTL readiness and understandable language for non-technical users.
- No hidden critical actions, no color-only meaning, no fabricated status, and no forced high-bandwidth experience when a useful fallback exists.

Target WCAG 2.2 AA; verify with automated checks and manual assistive-technology/device testing.

## 14. Reliability, observability and cost controls

- All uploads, jobs, publications, webhooks and financial operations are idempotent.
- Jobs have bounded retries, backoff, cancellation, deadlines, dead-letter/error state and operator visibility.
- Realtime loss falls back to refresh/reconnect where appropriate; the durable database remains authoritative.
- Monitor startup latency, playback rebuffering, upload completion, job duration/failure, live join/reconnect success, API errors, abuse and storage/egress costs.
- Set quotas and cost guards per user/workspace/provider; warn before costly operations; do not silently turn on paid infrastructure.
- Protect against unbounded prefetch, unbounded fanout, unbounded transcoding, oversized uploads and infinite retry loops.
- Keep sensitive payloads out of telemetry; define retention and access control for logs.

## 15. Implementation phases and acceptance gates

### Phase 0 — Architecture and evidence
- Keep this contract, the capability registry, Figma mapping and operational readiness register aligned.
- Inventory actual routes, components, schema, storage buckets, workers, providers and feature flags.
- Mark every capability implemented/partial/provider-required/planned/disabled; identify evidence owner and next test.
- Do not expand scope by deleting categories; prioritize delivery slices while retaining the full taxonomy.

### Phase 1 — Universal catalog and safe discovery
- Verify media-object/asset relationships, extensible IDs, capability registry and unknown-safe fallback.
- Implement authorized metadata, loading/empty/error/offline states and bounded pagination.
- Gate: unknown format cannot crash the feed or bypass privacy/moderation.

### Phase 2 — Reliable consumption and durable interactions
- Verify real playback for Shorts, long video and audio; single active viewport, queue/resume, adaptive delivery and captions.
- Verify react/comment/save/share/follow and reload persistence under real authentication.
- Gate: source data, playback, writes and refreshed state are real, authorized and tested.

### Phase 3 — Creation, processing and publishing
- Upload/resume, drafts, asset library, job status, transformation graph, moderation, scheduling and publication.
- Gate: real worker/provider contract, recoverable failures, rights/provenance and no fake completion status.

### Phase 4 — All live topologies
- Implement a real provider adapter and full lifecycle for each selected topology; do not collapse every live format into a generic room.
- Gate: host/viewer/participant flows, permissions, reconnect, moderation, recording consent, metrics and outage handling pass integration tests.

### Phase 5 — Spatial, interactive and hybrid experiences
- Capability negotiation, sandboxing, device permissions and graceful fallbacks.
- Gate: unsupported hardware and active content fail safely.

### Phase 6 — Creator, workspace, developer and operator systems
- Separate identity contexts; creator analytics and monetization; scoped developer keys/webhooks; audited admin/moderation tools.
- Gate: server authorization, RLS, least privilege, audit and abuse controls pass role-matrix tests.

### Phase 7 — Expansion without category ceiling
- Add new types through descriptors/adapters, update capability inventory and test contracts.
- Gate: a new media family can be registered and integrated without changing core navigation or rewriting the universal object model.

A phase is not complete because a screen exists. Completion requires automated tests, real provider/device checks where applicable, persistence and authorization evidence, accessibility review, production smoke testing and an updated readiness register.

## 16. Architecture decisions and anti-patterns

**Decisions**
- Fresh Flow is the canonical all-media ecosystem; no parallel “Fresh Media” product layer.
- Six destinations remain entry points, not a closed taxonomy.
- Media type and action IDs are extensible strings; capability registry is not an authorization system.
- One universal object/asset model plus specialized adapters and renderers.
- Durable state, ephemeral events and binary media are stored/delivered through the appropriate layers.
- All capabilities have explicit truthful availability and fallback states.

**Anti-patterns prohibited**
- Treating “all media” as only videos, images, podcasts or a finite six-tab list.
- One giant media enum or database migration required for every new format.
- Duplicating feed, identity, interactions, storage or authorization for each category.
- Fake viewer counts, fake analytics, fake balances, mock providers represented as production.
- Running arbitrary uploaded code or trusting client MIME/metadata.
- Assuming a provider, codec, device permission, payment method or AI model exists because a UI button exists.
- Putting binaries/secrets in Postgres rows or client bundles.
- Treating Broadcast/Presence as durable records or client counters as authoritative.
- Claiming E2EE, production-ready streaming, complete accessibility or full rollout without evidence.
